핸드오프 번들에는 `tokens.css`가 들어 있었고, 문서에는 이렇게 적혀 있었습니다 — "이 파일은 그대로 가져다 쓰는 것을 의도한 산출물입니다".

## 고치고 싶은 순간은 반드시 온다 {#temptation}

작업 이틀째에 벌써 고치고 싶어집니다. 여기 여백이 4px만 더 있으면, 이 회색이 한 단계만 밝으면. 한 번 고치기 시작하면 그 파일은 더 이상 계약이 아니라 그냥 내 CSS가 됩니다. 다음에 디자인이 갱신됐을 때 무엇이 내 손자국이고 무엇이 원본인지 구분할 수 없습니다.

그래서 규칙을 하나 세웠습니다. **원본은 파일 위쪽에 그대로 두고, 내가 쓰는 클래스는 아래쪽 별도 레이어에 쌓는다.**

```css:globals.css
/* ── 위쪽: 핸드오프 tokens.css 원본. 손대지 않음 ── */
@theme { --color-accent: oklch(0.70 0.15 278); }

/* ── 아래쪽: 프로젝트 레이어 ── */
@layer components {
  .archive__title { font-size: var(--text-h1); }
}
```

## 무엇이 쉬워졌나 {#what-got-easier}

값을 바꿀 수 없다는 제약이 결정을 줄여 줍니다. "이 회색이 애매한데"라는 생각이 들면 선택지는 둘뿐입니다 — 램프에서 다른 단계를 고르거나, 색이 아닌 방법(괘선, 여백, 굵기)으로 푸는 것.

보관된 프로젝트를 목록에서 흐리게 보일 때가 그랬습니다. 새 회색을 만들지 않고 `--color-text` → `--color-text-2`로 한 단계 내리는 것으로 끝났습니다. 결과적으로 팔레트가 늘지 않았습니다.

> [!NOTE]
> 예외는 문서가 명시적으로 허용한 곳뿐입니다. 이 시스템은 v0.2에서 토큰 7종을 추가했는데, 그것도 "기존 값은 변경·대체하지 않았습니다"라고 못박고 시작합니다.

## 남는 문제 {#open}

프로젝트 레이어가 커지면 결국 두 번째 시스템이 됩니다. 지금은 화면별로 구획을 나눠 두었지만, 화면이 열다섯 개가 되면 정리가 필요할 겁니다. 그때는 반복되는 패턴을 골라 컴포넌트 쪽으로 올리는 게 맞다고 봅니다.
