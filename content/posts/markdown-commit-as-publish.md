자동 게시 시스템을 설계할 때 가장 먼저 정해야 하는 건 "게시물이 어디에 사는가"입니다. 이 결정이 나머지 전부를 좌우합니다.

## 저장소를 데이터베이스로 {#repo-as-db}

게시물을 DB에 넣으면 게시 API가 필요하고, 인증이 필요하고, 백업이 필요합니다. 게시물이 저장소 안의 `.md` 파일이면 그 셋이 전부 GitHub의 몫이 됩니다.

```bash:publish.sh
git add content/posts/2026-07-28-commit-as-publish.md
git commit -m "post: 커밋이 곧 발행이 되도록"
git push
```

배포는 푸시에 붙어 있으니, 파이프라인의 마지막 단계는 말 그대로 커밋 하나입니다.

## 프론트매터가 스키마다 {#frontmatter}

파일 앞머리의 YAML이 곧 데이터 모델입니다. 여기에 `source`와 `source_ref`를 두는 게 핵심이었습니다 — 이 글이 손으로 쓴 것인지, 영상 요약에서 나온 것인지, 개발 로그에서 나온 것인지를 나중에 구분할 수 있어야 합니다.

> [!NOTE]
> 프론트매터를 늘리고 싶은 유혹을 참으세요. 본문에서 계산할 수 있는 값(읽는 시간, 소제목 목록)은 넣지 않습니다. 두 벌이 되는 순간 반드시 어긋납니다.

## 한계 {#limits}

이 방식이 불편해지는 지점은 분명합니다. 게시물이 수천 개가 되면 빌드가 느려지고, 여러 사람이 동시에 쓰면 충돌이 납니다. 둘 다 1인 블로그에서는 오지 않는 문제라, 올 때 옮기기로 했습니다.
