# 0005. 공개 화면의 DB 조회에 명시적인 캐시 정책을 둔다

- 상태: 채택
- 날짜: 2026-10-13

## 맥락

#8에서 글 18편을 서비스 롤로 직접 지웠는데, 아카이브는 비었지만 홈과 글 상세에는 지운 글이
그대로 보였습니다 — 로컬 빌드와 운영(Vercel) 모두.

추적해 보니 `.next/cache/fetch-cache`에 **2026-08-28에 저장된 글 목록이 유효기간 1년
(31536000초)** 으로 남아 있었고, `next build`가 DB를 다시 묻지 않고 그 항목을 썼습니다.
공개 Supabase 클라이언트의 fetch에 캐시 정책이 없어서, 각 조회의 수명이 그 라우트의 성격(홈은
HN 조회 때문에 ISR 1시간, 다른 곳은 정적)에 따라 암묵적으로 정해졌기 때문입니다. Vercel의
데이터 캐시는 배포 사이에도 유지되므로 재배포로도 풀리지 않았습니다.

관리자 화면의 저장은 `revalidatePath("/", "layout")`로 캐시를 비우므로 지금까지 드러나지
않았습니다. 관리자 화면을 거치지 않는 변경(DB 콘솔, 스크립트, 이번 같은 정리)이 처음이었습니다.

## 결정

`src/lib/supabase/public.ts`의 fetch에 정책을 명시합니다.

- `cache: "force-cache"`, `next.revalidate: 3600`, `next.tags: ["public-db"]`
- 요청 헤더 `x-index-cache-policy: v2` — fetch 캐시 키는 URL·메서드·헤더·본문으로만 정해지므로
  (`cache` 옵션은 키에 들어가지 않음), 정책을 바꿀 때 이 값을 올려야 예전 항목이 다시 쓰이지 않습니다.

## 대안

- `cache: "no-store"` — 항상 최신이지만 공개 화면 전체가 요청마다 렌더되는 동적 라우트가 됩니다.
- 그대로 두고 지울 때마다 관리자 화면을 거치기 — 규칙으로 막는 것은 한 번 잊으면 끝납니다.
- 재검증 API 라우트(비밀 키로 `revalidateTag`) — 즉시 반영이 필요해지면 추가합니다. 지금은 1시간이면 충분합니다.

## 결과

- 좋은 점: 어떤 경로로 DB가 바뀌어도 최대 1시간 안에 반영됩니다. 공개 라우트의 수명이 한 곳에서 정해집니다
  (빌드 출력에서 `/`, `/projects`, `/tags`가 모두 Revalidate 1h).
- 감수하는 점: 관리자 화면 밖의 변경은 즉시 보이지 않습니다. 정책을 바꿀 땐 `CACHE_POLICY`도 올려야 합니다.
